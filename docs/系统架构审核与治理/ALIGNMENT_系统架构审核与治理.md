## 2. 边界确认 (Scope & Boundary)

### 2.1 纳入治理范围 (In Scope)
1. **P0 安全漏洞修复**：重写 PostgreSQL Row Level Security (RLS) 策略，产出 `007_secure_rls.sql` 迁移，建立严密的鉴权与行级安全体系，防御任意提权与越权清库。
2. **P1 性能反模式重构**：在前端封装生产级 PostgREST 服务端分页助手 `serverPageOf`，原生利用 PostgREST `range` 和 `Prefer: count=exact` 机制，替代脆弱的内存全量排序与分页。
3. **P1 脚手架 CLI 修正**：修改 `packages/gravityd-cli` 代码生成模板，将 `"order"` 改为非保留字 `sort_order`，自动注入安全 RLS 和真服务端分页代码，确保单元测试 100% 通过。
4. **P2 遗留死代码与文档治理**：对前端失效的 `module_ai/chat`、`module_storage/transfer` 等模块进行安全降级与异常隔离，更新文档指示。

### 2.2 明确排除范围 (Out of Scope)
- 不复活 FastAPI 8001 主后端，恪守 GravityD BaaS 架构既定路线。
- 不破坏已有 `001-006` 迁移历史（绝不重跑 002）。

## 3. 需求理解与架构对齐

### 3.1 对 BaaS 架构的深度理解
在去除中心化后端服务后，数据库不仅是存储，更是**安全准入的第一道也是唯一一道防线**。
前端的鉴权校验仅用于提升 UI 交互体验；真正的权限控制、行级可见性、敏感字段更新保护，必须 100% 委托给 PostgreSQL 数据库引擎内置的 RLS 策略。

### 3.2 治理前置约束与条件
- 迁移序号：当前最新为 `006_brand_gravityd.sql`，本次治理迁移必须严格命名为 `007_secure_rls.sql`。
- 保证平滑兼容：现存业务账号 `admin@local.dev`（`profiles.id = 'cc49c595-0764-4ff8-b4e5-f13f5e696905'`）必须拥有超级管理员完全放行权限。
